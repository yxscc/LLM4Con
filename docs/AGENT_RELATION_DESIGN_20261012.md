# Agent 完成状态、契约状态和同步关系设计

状态：第 3、4、5 项的设计稿；除源码工具迁移所需的只读契约视图外，尚未修改正式契约 schema、结束条件和 E。不是新实验结果。

## 共同原则

- 保留源码主导的 `Req + Gua + CCPG → E`。不以协议记账、自然语言摘要或事实清单替代 Req 消解。
- 全部 supplied IR 定义/指令继续在静态模型中。全部输入源码可访问；不注入 AST，不按入口、对象桶或代表采样限制分析范围。
- Agent 应尽量提全有源码依据的并发安全需求，覆盖已经识别的资源、双方操作和事务；漏提 Req 会直接使 E 无法检查对应关系，影响召回。不要求形式化完备证明不等于接受随意少提 Req。
- 完成流程不等于找到全部问题。未知、不支持和部分抽取必须能保存，不能要求 Agent 建立完美同步逻辑才能结束。
- 召回仍由人工对照最终报告、轨迹、源码和历史修复，大致对应真实缺陷即可；以下状态不是 GT 标签。

## 3. Agent 的主任务：尽量提全真实 Req，结构化保存

主流程就是用户描述的流程：Agent 从源码识别并发需求，选择对应操作，注册/绑定源码操作，再通过 `add_requirement` 保存可解析的 Req；E 用这些 Req 检查图上的关系。注册操作和提交契约都返回绑定诊断，E 再解析有效操作；无法绑定的 Req 仍保留，不能因为静态后端暂不支持就不提交。

```text
阅读源码 → 识别安全需求 → 选择/注册操作并获得绑定反馈
         → add_requirement 保存结构化 Req → E 检查
阅读同步实现 → add_guarantee 保存结构化 Gua → 增强检查图
```

需求是否存在和代码是否已经满足需求是两个问题。即使看到锁、RCU 或引用计数，仍应提交有源码依据的 Req，同时提交相应 Gua，让 E 检查其操作覆盖和位置；不要因认为“应该安全”而提前省略 Req。普通局部顺序或没有并发冲突依据的字段则不应被虚构为并发 Req。

之前所说的“记账”仅指现有 `record_pattern_review`（记录六类问题如何调查）和 `record_protocol`（保存协议解释）这两个辅助日志。它们不是提交 Req 的工具，不参与 Req 消解。写了“已检查”“框架有锁”等日志，不能代替具体 Req/Gua。

不再建议新增一套 protocol position JSON 或把辅助日志变成更复杂的结束门槛。结束前主要检查已经发现的需求是否提交、已知错误契约是否修订，以及未绑定/不支持的位置是否保留。未知允许保存和结束；不存在固定对象或契约数量配额。

六类问题日志可以保留为调查线索，但不是抽取完备的证据。优化抽取遗漏仍通过人工阅读真实轨迹、源码和修复归因，不能用日志打勾或自动 GT 标签代替。

## 4. 契约状态：随时提交，持久化原始结构，按需恢复

现有行为保持：`add_requirement/add_guarantee` 每次调用即验证、保存；`replace_id` 修订已有记录，历史保留。不是最后一次性提交 Gua。

持久化状态包含当前有效 Req/Gua、源码操作、外部证据引用、修订历史和 E 检查结果。它是唯一权威状态；SDK 压缩只管理工作上下文，压缩摘要不能添加、修改或恢复规则。

源码工具迁移已提供只读 `contract_state.json`，由 SDK shell 读取实时原始账本。后续若需要便利接口，可提供：

```text
get_contracts(kind, ids, offset, limit) → 完整结构化记录、ledger_revision、next_offset
add_requirement/add_guarantee(...) → id、record_revision、ledger_revision、绑定诊断
```

`kind` 支持 requirements/guarantees/source_operations/revisions；分页只是响应大小控制，不能丢弃记录。稳定 ID 不因修订改变，版本递增；查询不能写入契约。SDK 会话跨 A/C 继续，但恢复正确性不依赖旧消息是否仍在模型上下文中。

任何抽取失败都对已接受账本尽力执行 E，同时保留错误和未完成状态。E 或报告恢复失败时，保留原始错误和实际 E 状态。

## 5. Gua 增强完整检查图，Req 查询该图

### 当前差异

当前 E 在每条 Req 内部筛选 Gua，要求 `resource` 和 `scope` 描述字符串逐字相同。Order/Wait 是查询中的虚拟边，Exclude 和 AtomicOp 是专门保护关系；原始 CCPG 没有被修改。

建议移除“每条 Req 必须有文字标签相同的 Gua”这一关联方式。也不引入 `req_id → gua_id` 的强制配对。Req 和 Gua 通过真实操作及同步适用域相遇，而不是通过需求名称相遇。

### 完整图构建

```text
完整 CCPG + 原始 Gua（绑定及证据检查） → 完整增强检查图 G*
每条 Req → 操作绑定 → 在同一个 G* 上执行相应规则
```

“独立”的意思是 Gua 建模不依赖某条 Req，不是同步关系脱离图。对 E 而言，CFG、同步边、保护区域和原子效果属于同一个完整逻辑图。实现可以直接存入增强图，也可以用 overlay 保存新增内容；统一图查询必须同时消费全部内容，不能只在 CFG 上检查后另看一张事实表。

可表示为 `G* = (V, E_CFG, E_CALL, E_SYNC, Regions, AtomicEffects, Domains)`。这里各关系有类型，不能将它们混合后做普通可达性闭包。原始 CCPG 可保留用于复现，E 直接使用增强图。新增、删除或改名 Req 不应改变同一组 Gua 构建出的图。

关系保留类型及来源：

- Order/Wait：带同步机制、事件端点、参与方和适用域的有向关系。
- Exclude：同一保护 token 下的区域排斥关系，保留连续保护区间；不能把锁简单转成任意操作的 HB 边。
- AtomicOp：保留当前单次操作原子效果兼容规则，不扩张为事务原子性，不重构类型体系。

每条关系附带 Gua ID/版本、源码证据、绑定节点、声明域、已满足和未解决的前提。一个 Gua 可以支持多个 Req，也可以在暂时没有 Req 时存在。

### 适用域

资源/作用域描述保留供人阅读，但不再作为字符串相等的求解门槛。可以为同步域定义稳定 ID，描述对象实例、激活参与方、生命周期或代际及成立条件。这个 ID 描述 Gua 自身的语义域，不是它所服务的 Req。

查询和关系组合仍须满足实际操作覆盖及域兼容：不能把不同锁实例、不同完成对象、不同代际或不匹配的参与方连接起来。声明相同 domain ID 本身不是别名或实例证明。编译器事实、源码证据或 Agent 声明支持多少就记录多少；无法建立兼容性时保留未知，不靠文字模糊匹配或自动猜别名消除。

同一同步 handoff 可能保护多种资源，所以同步对象名称不必等于 Req 所讨论的数据对象名称。

### Req 及消解规则

令 `≺G*` 表示完整增强图中包含至少一个适用同步 Gua、并经过局部 CFG 位置检查的顺序关系。普通同线程程序顺序仍不能直接消解跨激活 Req。

例如 `写 x → complete(c) ⇒ wait(c) 成功返回 → 读 x`：两端局部顺序由 CFG 检查，`⇒` 是同一完成对象及匹配激活中的 Wait 同步边。E 在完整图里组合这些有类型的关系，建立写在读之前；分支上的可能可达、失败/超时返回、调用导航和不匹配的同步域不能直接作为此顺序。

```text
MustPrecede(A,B):
  对每个适用组合 (a,b)，要求 a ≺G* b。

MustBeMediated(A,B):
  对每个指定冲突组合 (a,b)，要求适用的顺序、排斥或兼容单次原子效果。

MustBeAtomic(S,I):
  S 为同一激活、同次事务执行中可行且有序的依赖步骤；
  对每个指定且适用的干扰 i，不能出现 s1 ≺ i ≺ sn。
```

Atomic 的目标语义不变化。当前可保留的充分消解规则是，对每个 i 建立 `sn ≺G* i`、`i ≺G* s1` 或 `ContinuousExclude(S,i)` 之一。步骤的局部顺序是事务前提，不是跨线程同步。

未绑定或 CFG 不支持的操作保留未知；二元 Req 的已绑定组合仍可继续检查。事务 S 不完整时，不能用剩下的步骤代替完整事务。单次 AtomicOp 不能消解多步骤原子需求。

E 输出应分清已检查的操作组合、所用 Gua 链/保护区域、失败的充分规则和未解决前提。未消解仍是候选，不是可执行反例或已证明漏洞。

### 验证与边界

先用冻结账本做零模型 replay，再进行多个案例的人工对照：

1. 只改 Req 的显示名称/resource 描述，已有同步关系层应不变。
2. 没有 Req 时也能构建 Gua 关系；添加 Req 不改变关系层。
3. 同一同步关系可支持多个不同资源的 Req，但不跨不兼容实例/参与方/代际。
4. 保留无同步 Gua 时不能靠局部 CFG 顺序消解、连续区域保护、部分绑定和 unknown 等回归。
5. 原始 native 结果、修改实现后的 replay 和手工诊断输入分别保存。

已有的端到端 Gua 端点问题、循环 occurrence 和一般跨过程 must-order 仍是独立边界。本设计不声称仅移除文字标签门槛就修复了这些问题；按用户约定暂缓相应重构。
