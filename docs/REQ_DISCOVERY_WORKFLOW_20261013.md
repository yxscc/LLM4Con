# 从共享状态发现 Req 的抽取流程

本轮优化的主问题：Agent 已读到目标代码，却经常从 lock/work/ref/teardown API 出发，将整个模块解释为几个看起来安全的协议。这样会漏掉普通共享字段、协议外读者、同入口并发、放锁后尾访问、子对象和硬件参与者。此前48例人工归因中，39例主要落在阅读/Req提取；不是通过增加绑定成功率就能解决全部问题。

## 实际改动

Phase A 现在默认包含两个连续的源码抽取步骤：

1. **状态需求发现**：从真实读取、更新、使用、发布、复用和失效操作出发，识别实例、参与者和安全需求；随发现随提交 Req/Gua。已有保障可以满足需求，但不能成为省略真实 Req 的理由。局部状态、允许的中间状态和普通API前提仍不能被强造为并发需求。
2. **源码需求扫描**：继续同一官方 SDK 会话，在执行 E 之前，针对普通字段/RMW、同入口多激活、保护域外读者、真正发布点、表面完成后的访问、子对象/代际、错误回滚、硬件消费者，再对照原始 Req 操作集合调查遗漏。可以增加新 Req，或通过 replace_id 改正错误操作/参与者/结束边界；也可以修改真实 Gua。没有必须新增多少 Req 的配额。

第二步不输入 E 结果、GT、修复或自动阶段标签，不产生漏洞确认/否判，不是 Phase C。普通源码工具、同版本依赖查询、原始契约账本和 SDK 历史均继续使用。没有新增摘要 Agent、手工模型循环、入口裁剪或静态对象桶。全部源码/IR范围不变。

用两步的原因是改变实际调查过程：第一步的同步机制解释容易锚定后续判断；第二步明确从状态访问和漏掉的参与者反查已有解释。它是待真实多案例验证的召回优化假设，不是抽取完备保证，不能以Req数量增加宣称提升。

## 支撑修复

- finalize_contract 除原有目录问题审阅外，检查当前接受契约的诊断是否已查看。契约或源码映射改变后，旧诊断不能继续充当检查结果。
- 接受契约引用的未绑定操作若已有IR候选，需要按 source_id 查询实际指令；恢复对应，或用 record_gap(source_ids=...) 保存仍未知的具体原因。真正无IR候选的操作可保留unknown；未用于契约的普通导航锚点不会阻止结束。这个门槛只处理已知抽取问题，不证明代码已全面覆盖。
- 抽取反馈保留 local_path 与 cyclic_local_path，同时新增 e_sequence_order，报告E实际要求的局部顺序前提。尤其指出可达但不支配的情况，避免HCI那样单个compiler arm被当成完整源码检查。循环和一般跨过程仍可保持不支持；不删除真实步骤来让检查器通过。
- 第二步异常时保留第一步已接受 Req/Gua，继续部分E，并保留非零退出/partial_extraction。结束条件不要求未知全部消失。
- 批次usage统计识别实际完成的抽取步骤，避免把两次SDK运行误记为usage不完整或遗漏第一步费用。

## 对照与运行

默认 requirement sweep 为 on。可以设置 LACE_REQUIREMENT_SWEEP=off，或通过 run_module/run_batch 的 --requirement-sweep off，在同代码/同输入/同模型下对照第二步的增量作用。初始状态导向提示和一致性检查在on/off两组都保留；这不是整个旧版本与新版本的单变量消融。

默认 max-turns 仍为0。显式正数限制作用于每次SDK调用，报告新增 max_turns_per_sdk_invocation 说明其含义，旧字段保留兼容。压缩依然使用已有SDK机制；当前网关的Chat Completions配置不会因此变成已启用原生压缩，也没有通过丢历史模拟压缩。

工程验证与模型评估分开：先测试两步连续会话、合法unknown结束、陈旧诊断拒绝、第二步失败的部分E、可选Phase C、usage汇总及旧E回归。随后冻结实现和输入，在不同机制的真实development病例上比较原生报告和人工源码归因。GT只用于事后人工评价；手工probe不计入原生召回。

已完成：隔离工作树完整构建、5项CTest、24项SDK/源码工作区/仓库Python测试、6组localhost流程验证（OA两步及绑定恢复、CAN关闭第二步、ioprio两步接可选C、第二步context错误、第一步预算耗尽、第一步API错误）。ioprio初试未配置正常的pinned源码核验，重复别名使测试的宽源码锚点无候选；接入正常核验/去重后通过。初试失败日志单独保留，没有替换数据集输入。

tests/req_discovery_plan.json 的七例冻结原始账本已零模型重放，新二进制的E结果与原生checks逐项相同。原模型、账本和报告未修改。该计划覆盖普通共享字段、解锁后访问、发布、CPU/硬件及子回调寿命，并保留绑定正例；真实Agent对照尚未启动。验证原始记录在远端 lace-req-discovery-offline-20261013。

开发split为上述七例；另有validation split的OA/CAN/ioprio三例，用于人工检查已有对应报告和Req/Gua是否退化。它们不会向Agent提供GT/修复或自动评分规则。先比较真实需求、操作/参与者及进入E的关系，再按既有宽松口径对照最终报告。

## 保留与后续

Req三种形式和E消解规则不变；Gua仍描述代码实际同步效果。独立Gua增强图的设计继续参考 AGENT_RELATION_DESIGN_20261012.md，本轮没有实现它。现有精确resource/scope匹配、Gua端到端端点、循环occurrence、完整跨过程关系和AtomicOp体系也没有在此次修改中被宣称解决。

第二步会增加模型请求和历史长度，需要实测增量召回与成本。如果仅重复已有结论，应调整调查组织，不以更多轮数/更多Req为成功指标。对“读取关键语句却漏提”的改善，必须看新轨迹是否建立了真实需求及正确操作/参与者，而不是看审阅打勾。
